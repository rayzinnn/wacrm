## Endpoint de envio de texto

O roteador registra `POST /message/sendText/:instanceName`; a composição do router monta `MessageRouter` em `/message`, e `routerPath('sendText')` acrescenta `/:instanceName`. Os guards de existência/logged-in e `apikey` são executados antes do handler. O handler valida o body, delega ao controller e devolve HTTP 201 com o valor retornado, sem envelope `{data: ...}`. [R1](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/routes/sendMessage.router.ts#L54-L63), [R2](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/routes/index.router.ts#L38-L42), [R3](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/routes/index.router.ts#L217-L220), [R4](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/abstract/abstract.router.ts#L20-L63).

### Request

Body mínimo de acordo com o schema: `{ "number": "...", "text": "..." }`.

| Campo | Situação no código | Limites e observações |
| --- | --- | --- |
| `number` | Obrigatório no schema; string | Sem regex, formato E.164, comprimento mínimo ou regra de país no schema. O serviço passa o valor por `whatsappNumber()`/`createJid()` e confere existência para usuário, ou consulta o grupo. Formatos aceitos pelo helper não equivalem a homologação de identidade WACRM. |
| `text` | Obrigatório no schema; string | O método rejeita texto vazio ou só espaços (`trim().length === 0`); preserva o texto original para a mensagem. |
| `linkPreview` | Opcional, boolean | Passado à chamada Baileys. |
| `delay` | Opcional, integer em milissegundos | Produz estados de presença/typing e espera antes do envio; valores acima de 20 s são divididos em intervalos. |
| `quoted` | Opcional | O schema descreve `key.id` obrigatório se `key` for fornecida; `remoteJid`, `fromMe` e `message` aparecem como opcionais. É passado ao serviço, que pode consultar a mensagem citada. Não faz parte do primeiro corpo mínimo C5. |
| `mentioned` | Opcional, array de strings | Schema exige ao menos um item, sem duplicatas, com padrão numérico `^\\d+`; passa à lógica de menções de grupo. Não é necessário para conversa individual de texto. |
| `everyOne` / `mentionsEveryOne` | **Divergência de schema/DTO** | Schema declara `everyOne`; DTO/controlador usam `mentionsEveryOne`. `dataValidate` aplica `Object.assign` e não remove propriedades extras, mas o código não comprova que `everyOne` tenha efeito. Não depender desse campo. |

O DTO base também declara `encoding` e `notConvertSticker`, mas o schema de texto não os define e `textMessage()` não os encaminha. `webhookUrl` aparece em `Options` de outras mensagens, não no schema/DTO de texto. Não tratá-los como opções de texto suportadas. [R5](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/validate/message.schema.ts#L41-L93), [R6](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/dto/sendMessage.dto.ts#L3-L52), [R7](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/abstract/abstract.router.ts#L29-L63).

### Destinatário e autenticação

O header é `apikey`. O guard aceita a chave global configurada; caso contrário, procura `instanceName` da rota e compara o header com o token daquela instância. Não é Bearer. O endpoint de envio recebe credencial no header, não no JSON. [R2](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/routes/index.router.ts#L38-L42), [R8](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/guards/auth.guard.ts#L10-L51).

`createJid()` preserva JIDs explícitos com `@s.whatsapp.net`, `@lid`, `@g.us` e `@broadcast`; para entradas sem domínio remove espaços, `+` e parênteses, separadores/dígitos conforme a função e acrescenta domínio. Há regras específicas para números BR/MX/AR e heurísticas que podem classificar strings longas como grupo. `whatsappNumber()` valida usuário ou procura grupo antes de envio. Portanto, não há uma única normalização segura que possamos copiar por suposição. Para o primeiro corte, limitar a destinatário individual, fixar o formato após observação local e recusar grupo, broadcast e status. [R9](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/utils/createJid.ts#L1-L71), [R10](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L2289-L2303), [R11](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L3507-L3567).

### Fluxo e retorno derivado do código

```text
POST /message/sendText/:instanceName
  → guards (instância, sessão, apikey)
  → schema/body validation
  → SendMessageController.sendText(instance, dto)
  → waInstances[instanceName].textMessage(dto)
  → valida text não vazio
  → sendMessageWithTyping(number, {conversation: text}, options)
  → whatsappNumber(number)
  → Baileys client.sendMessage(jid, {text: conversation, ...options})
  → prepareMessage(WAMessage) → HTTP 201 + JSON(messageRaw)
```

O objeto `messageRaw` é derivado do `WAMessage` retornado por Baileys: `key` copiada, `pushName`, `status`, `message`, `contextInfo`, `messageType`, `messageTimestamp`, `instanceId` e `source`. `messageTimestamp` é convertido de Long para number. O código transforma `extendedTextMessage.text` em `message.conversation`. A resposta preserva `key.id`, `key.remoteJid` e `key.fromMe` que vieram de Baileys; o contrato não substitui esses valores nem fixa um exemplo. A enumeração interna de status é `ERROR`, `PENDING`, `SERVER_ACK`, `DELIVERY_ACK`, `READ`, `DELETED`, `PLAYED`; para `fromMe === false` apenas, `prepareMessage` usa `DELIVERY_ACK` como fallback quando status não veio. Logo, HTTP 201 não comprova entrega, e o status de uma resposta outbound pode estar ausente. Essa é leitura estática do fluxo; **nenhum body real foi capturado**. [R12](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/controllers/sendMessage.controller.ts#L31-L40), [R13](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L2628-L2649), [R14](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L2130-L2287), [R15](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L2421-L2450), [R16](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L4652-L4703), [R17](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/utils/renderStatus.ts#L1-L10).

O POST chama `client.sendMessage` uma vez no fluxo de texto e não tem request ID ou idempotency key no schema/controller. Não há retry de envio no caminho mostrado. `BaileysMessageProcessor` pode reexecutar o **handler de processamento de `messages.upsert`** até três vezes após erro, com intervalo de um segundo; `WebhookController` tem retry próprio configurável para POST do webhook (defaults no código: 10 tentativas, intervalo inicial 5 s). São retries de callback/processamento, não autorização para repetir `sendText`; o receiver WACRM ainda precisa deduplicar eventos duráveis. Timeout depois da aceitação remota fica ambíguo. [R14](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L2130-L2287), [R18](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/baileysMessage.processor.ts#L38-L69), [R19](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/event/webhook/webhook.controller.ts#L203-L242).


### Erro HTTP 400 também pode ser ambíguo

Revisão posterior do mesmo SHA: `sendMessageWithTyping` chama Baileys e depois executa preparação/persistência Prisma antes de retornar. O `catch` abrangente converte exceções dessa região em `BadRequestException(error.toString())`. Assim, uma falha após aceitação remota pode produzir HTTP 400. O cliente WACRM deve tratar HTTP 400 de envio como `ambiguous=true`, `retryable=false`, sem interpretar o texto bruto para afirmar rejeição. Não classificar toda resposta 4xx como prova de que nada foi enviado. [Fonte fixada — envio e persistência](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L2387-L2460), [conversão da exceção](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts#L2557-L2561).


## Eventos de mensagem

O envelope enviado pelo webhook tem `event`, `instance`, `data`, `destination`, `date_time`, `sender`, `server_url` e `apikey`, possivelmente com `extra`. `event` é o nome lower-case com ponto; lista de seleção interna usa chaves upper-case como `MESSAGES_UPSERT`/`MESSAGES_UPDATE`. Não salvar o envelope bruto: C2 persiste somente projeção normalizada, sem `apikey`, `server_url`, `destination` ou `extra`. [R20](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/services/channel.service.ts#L435-L463), [R21](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/event/webhook/webhook.controller.ts#L88-L103), [R22](https://github.com/evolution-foundation/evolution-api/blob/cd800f2976e1e5b682fbf86a01ee4d85ae61f370/src/api/integrations/event/event.controller.ts#L138-L170).

| Emissão | `data` que o handler constrói | Relação com C2 |
| --- | --- | --- |
| `messages.upsert` | Um `messageRaw` por mensagem no loop, para mensagens com `type` `notify` ou `append`, fora do caminho de edição e com `message`. Mantém `key`, `message`, `messageType`, `messageTimestamp`, `status`, `pushName`, `contextInfo`, `instanceId` e `source`. `key` retém `id`, `remoteJid`, `fromMe` e outros campos Baileys. Extended text vira `messageType='conversation'` e `message.conversation`; `@lid` pode ser substituído por `remoteJidAlt`. | `externalMessageId ← data.key.id`; `peer ← data.key.remoteJid` após transformação (não inferir que é telefone); `fromMe ← data.key.fromMe`; mapear texto só de tipos confirmados. `messageTimestamp` é candidato para `occurredAt`, mas unidade/ordem e LID devem ser confirmados com callback real. Não filtra `fromMe=true`: eco de aparelho/API também pode aparecer. |
| `messages.update` | Um objeto por par `{key, update}`: `{keyId, remoteJid, fromMe, participant, status, pollUpdates, instanceId}` e `message` opcional. `status` usa mapeamento local; quando `update.status` não resolve, o código usa `SERVER_ACK`. A projeção não inclui `messageTimestamp`. | `externalMessageId` candidato é `keyId`; `peer ← remoteJid`; `fromMe ← fromMe`. C2 status candidato: `SERVER_ACK→sent`, `DELIVERY_ACK→delivered`, `READ→read`, `ERROR→failed`. `PENDING`/`PLAYED` não cabem no estado C2 atual; ignorar/recusar explicitamente até contrato. Como o update não leva timestamp próprio, usar tempo de recebimento WACRM ou revisar C2; `date_time` do envelope é criado como hora local serializada com `Z`, não é timestamp remoto confiável. |
| `send.message` | `textMessage()` chama `sendDataWebhook(Events.SEND_MESSAGE, messageRaw)` e então retorna `messageRaw` ao POST. | É a evidência de código mais direta para classificar uma ação REST como `sentByApi=true`; `fromMe` sozinho só distingue enviado/recebido no WhatsApp e não explica se a origem foi REST ou aparelho. Correlacionar `key.id` com eventual `messages.upsert` antes de unir os dois em um evento C2. |

**Cuidado de ID:** durante `messages.update`, a implementação pode substituir `message.keyId` pelo ID recuperado do cache de protocolo (`protocol_<key.id>`); quando histórico está ativo, também adiciona `messageId` interno. Validar que o `keyId` emitido ainda corresponde ao ID remoto do C2 antes de usar como correlação. Atualizações que chegam sem a mensagem original no banco podem ser ignoradas pelo próprio serviço se `SAVE_DATA.HISTORIC` ou `NEW_MESSAGE` estiver ativo. ### Log de payload no código-fonte

No handler `messages.upsert`, `console.log(messageRaw)` é incondicional na linha 1481, imediatamente antes de `sendDataWebhook(MESSAGES_UPSERT, messageRaw)`. Não está protegido por nível `LOG`, flag ou logger configurável neste ponto; o `logger.verbose` anterior não controla esse `console.log`. A fonte pode enviar conteúdo bruto de mensagem a stdout do serviço. Isso é um **achado estático**: não observamos stdout nem payload real e não alteramos o código nem a imagem/containers. Remediação pertence a tarefa separada. ## Compatibilidade com C2/C5 e bloqueios

### C2 — projeção candidata, pendente de observação

- Aceitar apenas conversa individual de texto neste primeiro recorte. Para upsert textual, `messageType='conversation'` ou texto de `extendedTextMessage` normalizado em `message.conversation`; a fonte também envia tipos não textuais.
- `eventKey` determinístico por conexão deve derivar de ID remoto estável (`key.id` para upsert; `keyId` para status somente após confirmar que o cache não o altera). Não usar hash do corpo, `messageTimestamp` ou `date_time` como substituto de ID.
- `fromMe=false` pode representar cliente; `fromMe=true` não diferencia sozinho telefone pareado de envio REST. `sentByApi=true` só pode ser atribuído com vínculo do evento `send.message`/resposta de API e correlação real por ID.
- Status sem timestamp remoto não pode ser ordenado por `date_time` da Evolution. Receiver deve fixar seu próprio `receivedAt` UTC e estado aplicar progressão monotônica; estados anteriores à mensagem continuam pendentes conforme C2/schema.
- Não persistir envelopes brutos, payloads `extra`, tokens, `apikey`, URLs ou mensagem fora do escopo. `MESSAGE_UPSERT` pode carregar conteúdo de mídia; mídia privada não está homologada.

### C5 — contrato local e status da capability

Este trecho registra o contrato derivado da fonte no levantamento T03.d1. A decisão atual de ativação e seus checks estão em [T10.activation](evidence/T10.activation.md).

- `sendMessageToConversation(db, accountId, params)` preserva o contrato do CRM; `requestId` é interno e nasce antes do transporte, com reserva C3 (`reserve_evolution_send`). A API Evolution analisada não recebe nem garante idempotência para esse request ID.
- Enviar no máximo um POST para cada reserva vencedora. Mesma chave/corpo existente não chama transporte novamente; timeout, crash depois de possível aceite ou resposta incompleta persistem `unknown` e não autorizam novo POST.
- Uma resposta HTTP 201 com `key.id` pode fornecer candidato a `external_message_id`; status `sent` só após política C5 aprovada. `delivered/read/failed` dependem de `messages.update` observado. O HTTP 201, o campo status eventualmente ausente e `send.message` não são prova de delivery.
- Tipos fora da capacidade ativa devem ser recusados antes da chamada remota: mídia, localização, áudio de WhatsApp, stickers, contatos, templates, reações, polls, list/buttons, status/broadcast e JIDs de grupo. Em inbound, tipos de evento fora da união C2 são ignorados ou falham com código sanitizado explícito, nunca convertidos em texto fictício.
- No T03.d1, manter `getEvolutionCapabilities().text === false`, mídia vazia e as ações sem suporte bloqueadas. A ativação posterior mantém mídia vazia e ações sem suporte bloqueadas; este levantamento não alterou cliente, rota, schema, fixture, serviço nem chamada externa.

## O que observar depois de parear

O trecho abaixo é lista de homologação futura; não foi executado neste cartão. Usar destinatário de teste que o operador confirmar e não enviar sem autorização específica.

1. Capturar, sanitizando dados pessoais, uma mensagem inbound textual individual: envelope externo, `event`, shape de `data`, tipo Baileys, `key.id`, `remoteJid`, `fromMe`, `messageTimestamp`, status e conteúdo `conversation`. Confirmar valor numérico e unidade do timestamp.
2. Comparar os formatos de `number` e resultado/JID para o número de teste com/sem `+`, uma variação formatada local e o JID retornado por Evolution. Não generalizar a regra BR/MX/AR sem esses casos.
3. Após envio deliberado de uma única mensagem teste, guardar a resposta HTTP 201 sanitizada e conferir `key.id`, `remoteJid`, `fromMe`, `messageTimestamp` e `status`. Ver se o mesmo ID aparece em `send.message`, `messages.upsert` e/ou `messages.update`, e em qual ordem. Não repetir POST por timeout.
4. Observar uma mensagem enviada manualmente no aparelho para comparar `fromMe`, `send.message` e `messages.upsert`. Isso determina se C2 pode distinguir eco de aparelho e API por evento mais ID.
5. Observar callbacks reais `messages.update` para SERVER_ACK, DELIVERY_ACK, READ e uma falha controlada, se disponível. Confirmar `keyId` contra o `key.id` original, presença/ausência de timestamp, valor de `status`, ordenação e replay/duplicação.
6. Verificar como o handler transforma LID em `remoteJidAlt`; escolher uma identidade canônica só com prova. Grupos, broadcast, status, poll, reaction, location, sticker e interativos continuam excluídos.
7. Validar reentrega/retry de webhook com duas callbacks equivalentes e confirmar `eventKey` estável; separar retransmissão de webhook de reenvio remoto. Confirmar a configuração de exposição de `apikey` sem registrar o valor.
8. Planejar remediação independente do `console.log(messageRaw)` antes de qualquer teste que exponha conteúdo real em stdout; este levantamento não a executa.

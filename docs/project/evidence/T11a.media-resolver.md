# Evidência T11a — resolver de mídia Evolution

## Escopo executado

Implementados somente `src/lib/whatsapp/evolution/media.ts` e `media.test.ts`. O módulo é marcado `server-only`, recebe credenciais já resolvidas pelo chamador e uma `EvolutionMediaRef` estrita (versão 1; somente JID, ID e `fromMe:false`). Não foi conectado a webhook, worker, Storage, SQL ou UI. `getEvolutionCapabilities().media` continua inalterado e vazio.

O resolver constrói apenas `POST /chat/getBase64FromMediaMessage/{instance}` na origem validada por `assertAllowedEvolutionOrigin`, envia o token exclusivamente no header `apikey`, corpo limitado à chave e `convertToMp4:false`, `redirect:'manual'` e timeout de 15 segundos. Resposta não 2xx/redirect, erro de rede, timeout ou schema inesperado produz `EvolutionMediaError` com mensagem fixa e sem corpo/URL/detalhe bruto do provedor.

O corpo JSON é lido com limite de streaming de 16 MiB de bytes decodificados mais overhead JSON/Base64 limitado. O decoder exige Base64 canônico, compara o comprimento declarado quando presente, restringe `mediaType` e MIME, verifica assinatura compatível, exige extensão de nome compatível e sanitiza o filename. Retorna bytes, MIME, tipo CRM, nome seguro e SHA-256. Isso não habilita nenhum tipo de mídia do produto.

## Limites

Nenhum endpoint real foi chamado; nenhum token real, evento, mensagem ou blob foi lido; nenhum download, envio WhatsApp, mudança Supabase, webhook ou capability foi feito. Supabase não foi integrado neste recorte.

A allowlist aplicada é a do helper WACRM existente. T11a não resolve nem fixa DNS e não valida política de egress; essa proteção continua gate obrigatório antes de conectar o resolver a qualquer rede real. A checagem de bytes é assinatura/estrutura inicial, não validação profunda ou antivírus. A compatibilidade do schema de resposta com arquivos reais e os tipos aceitos pelo Evolution/WhatsApp continuam indisponíveis. A implementação futura deve continuar com mídia desativada até cada tipo passar pelos gates de T11.

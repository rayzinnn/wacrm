## Containers e Docker

Comandos somente leitura:

```sh
source /Users/raymozer/.local/share/wacrm-infra-a/env.sh
docker context ls --format '{{.Name}}\t{{.DockerEndpoint}}'
docker --context colima-wacrm ps --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'
docker --context colima-wacrm ps -q | while read id; do
  docker --context colima-wacrm inspect --format '{{.Name}} status={{.State.Status}} health={{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}} restarts={{.RestartCount}}' "$id"
done
```

Resultado: nove containers WACRM estavam `running`. Evolution API, Postgres e Redis estavam `healthy`; Supabase DB, Auth, Storage, Realtime e Kong estavam `healthy`; Supabase REST estava `running`, sem healthcheck configurado. Contadores cumulativos observados: Auth 3 restarts e REST 1; os outros, 0. Não inferi que esses contadores representem uma queda atual.

O Docker CLI sem contexto explícito primeiro não estava no `PATH`; após carregar o `env.sh`, seu wrapper foi encontrado. O contexto `default` aponta para `unix:///var/run/docker.sock`, que não existe neste host, e `docker ps` falha nesse contexto. O contexto já existente `colima-wacrm` aponta para `~/.colima/wacrm/docker.sock` e retornou os nove containers normalmente. Correção operacional: usar `docker --context colima-wacrm` nas consultas deste perfil; não alterei o contexto global.

## Probes HTTP

Todas as probes foram GET localhost, sem cookies, com body descartado por `curl --output /dev/null`; os tempos são de uma execução, não um benchmark.

Comando usado (URL e limite variaram conforme a tabela):

```sh
limit_s=6 # use 10 for the repeat probe
url=http://127.0.0.1:<porta>/<path>
curl --silent --show-error --max-time "$limit_s" --output /dev/null \
  --write-out 'http=%{http_code} total_s=%{time_total} connect_s=%{time_connect}' \
  "$url"
```

| Endpoint | Limite e resultado | Observação |
| --- | --- | --- |
| `http://127.0.0.1:3000/` | timeout de 6 s: HTTP 000, 6,112 s, connect 0,0006 s | Na repetição de 10 s: HTTP 307, 9,087 s, connect 0,0061 s. Redirecionamento esperado, mas lento. |
| `http://127.0.0.1:3000/login` | limite de 10 s: HTTP 200, 2,892 s, connect 0,0005 s | Página pública respondeu. |
| `http://127.0.0.1:54321/auth/v1/health` | primeira: HTTP 200, 4,132 s; repetição: HTTP 200, 0,981 s | Auth respondeu; latência variou. |
| `http://127.0.0.1:8080/` (Evolution) | timeout de 6 s: HTTP 000, 6,005 s, connect 0,0005 s | Na repetição de 10 s: HTTP 200, 8,767 s, connect 0,0485 s. |

Nesta rodada, os dois timeouts a 6 s ocorreram porque as respostas terminaram depois desse limite, e não por recusa de conexão: as mesmas URLs completaram em aproximadamente 9 s e retornaram 307/200 com limite de 10 s. Os containers e healthchecks estavam ativos. A demora depois do connect é observada, mas sua causa interna não foi isolada; o caminho das portas expostas também passa pelo forward SSH do runtime Lima.

## 503/timeouts anteriores e ação recomendada

- O coordenador havia informado que quatro `npm run typecheck` simultâneos por 5–8 min causaram 503 local. Essa concorrência é a causa concreta registrada para aquele episódio, reportada operacionalmente; não foi reproduzida aqui e nenhum typecheck foi iniciado. A ação para F8 é serializar o typecheck e evitar concorrência com outros checks pesados no Next dev/runtime.
- Nesta rodada, o limite de 6 s causou os dois timeouts de probe descritos acima; com limite de 10 s, ambas completaram. A latência de aproximadamente 9 s ainda merece investigação se persistir. Recomenda-se repetir poucas probes sequenciais e, se a demora continuar, revisar métricas de CPU/memória do Next e do runtime e consultar somente linhas de erro sanitizadas do Next/Evolution, nunca payloads ou credenciais.
- Há um 503 histórico diferente em `T03.c1.md`: primeira tentativa de callback da probe Evolution recebeu 503 e a repetição idêntica recebeu 200 após 5,044 s. Aquela evidência não atribui causa raiz ao 503; ele não prova falha atual do endpoint de health nem deve ser confundido com o incidente de typechecks simultâneos.

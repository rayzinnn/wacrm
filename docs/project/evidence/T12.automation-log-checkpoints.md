# T12 — registros das etapas de automação

Três migrations locais (`20261116225020`, `20261116225933` e `20261116230135`) acrescentam um item ao log para cada etapa Evolution concluída pela RPC `complete_evolution_dispatch_step`, sem duplicá-lo no replay. A conclusão da root e o status do log agora ocorrem na mesma transação quando há log vinculado. Roots antigas sem log preservam a validação e a conclusão anteriores; a preparação de candidatas incompatíveis pode continuar marcando `skipped` antes de criar um log.

O item registra o ID da ação e o ID distinto do ledger. Um resultado de entrega incerta permanece `outcome_state=unknown` no detalhe; o log geral usa `partial` quando a root fica incerta. Como as RPCs antigas limpam o token ao concluir, um replay de resultado já terminal só pode conferir conta, vínculo e payload idêntico, sem validar um token histórico. Um novo append exige leases vigentes.

O teste `evolution-automation-log-checkpoints.sql` passou com `BEGIN/DO/ROLLBACK`, incluindo replay, conta, leases e finalização pela assinatura atual. As suites SQL existentes de step e root também passaram. A migration foi aplicada apenas no Supabase local `127.0.0.1:54322`; o advisor de segurança em nível de erro retornou zero problemas. A fixture terminou sem contas, conexões, eventos ou usuários sintéticos residuais.

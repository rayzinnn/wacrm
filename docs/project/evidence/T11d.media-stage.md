# T11d — private Evolution media storage stage

## Implemented

- Added `src/lib/whatsapp/evolution/media-storage.ts`, a server-only adapter that writes only to the private `evolution-media` bucket using the service-role admin client. It never creates or returns a public URL.
- The adapter derives `account_id` from the event's `connection_id` and an Evolution-provider connection row before any Storage operation. It does not accept a caller-supplied account ID; unexpected input fields are rejected. It also checks the current processing lease before upload.
- Object paths are deterministic and match `stage_evolution_media`: `account-<account uuid>/evolution/<event uuid>/payload.<extension>`. Uploads use `upsert: false`; a collision is downloaded and accepted only when byte length and SHA-256 match. The adapter calls the existing fenced stage RPC and maps `staged`, `duplicate`, `stale`, and `conflict` without logging raw errors or media data.
- Added focused mocks in `media-storage.test.ts` for deterministic upload, injected cross-tenant account rejection with zero Storage/RPC I/O, stale lease before upload, non-Evolution connection rejection, same-hash/size replay, conflicting bytes, crash after upload before stage, stale result from the RPC, and replay after stage commit.
- `getEvolutionCapabilities().media` remains `[]`. No live Storage call, Evolution fetch, WhatsApp send, SQL edit, route/UI/capability change, or migration was made.

## Worker integration blocked by current contracts

The new adapter exposes the safe upload-and-stage step, but it is not wired into `message-worker.ts` yet. The current `apply_evolution_event` RPC requires non-empty text, requires `contentType='text'` and `mediaRef=null`, and permanently marks media events as `unsupported_message_content`. `stage_evolution_media` only stores metadata and leaves the event in `processing`; it has no release/terminal transition. The current claim RPC will reclaim expired processing rows and exhaust attempts. Calling the existing apply RPC after staging would therefore orphan the staged media behind a failed event; returning success would leave the row leased until it is reclaimed. No worker outcome was invented for this incomplete lifecycle.

The queue also marks all current media events failed while capability is empty, as expected. Separately, the T11a resolver is local-development-only and rejects the HTTPS origins used by deployed Evolution connections, so a real inbound worker could not safely download production media yet.

Local unblock: extend the existing apply RPC transaction to accept only a validated `media_state='stored'` event with matching event/connection, MIME, size, hash, deterministic path, and lease, and atomically create the message plus mark the event done; then integrate the worker/recovery flow and synthetic fixtures. Keep media capability empty until those checks pass. The already configured literal `127.0.0.1` origin is sufficient for local resolver tests. External Evolution origins remain out of scope until a pinned-destination transport or equivalent egress guard is implemented. If stage must be resumable independently, add a fenced SQL transition that releases the lease without resetting stored media and ensure the claim RPC does not repeatedly reclaim staged rows before final apply.

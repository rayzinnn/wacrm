# T10.b+c — core Evolution e rotas de envio

Data: 2026-11-16. Integração local do adapter T10.a ao core de envio de texto e aos dois chamadores HTTP autorizados.

## Comportamento

- Texto exige `requestId` estável no core e `Idempotency-Key` não vazio (até 200 caracteres) nas rotas. A chave vem do chamador; o core não gera identidade aleatória. A rota dashboard valida a chave antes de criar conversa; a rota v1 valida antes de resolver conversa.
- O core carrega a conexão Evolution da conta, reserva pela RPC antes do único POST permitido e usa o resultado persistido pela reserva/conclusão. Replay não faz POST nem cria mensagem local duplicada; reaplica o resumo da conversa e tenta pausar o flow ativo. Falha ambígua retorna `delivery_unknown`/504 e pausa o flow ativo, sem repetição.
- O envio de texto não usa `sendTextMessage`/Meta. Tipos diferentes de texto são bloqueados nas duas rotas com HTTP 422 `unsupported_capability`; capability e composer não foram alterados. Caminhos legados do core permanecem para o recorte de remoção/bloqueio.
- Autorização, papel, escopo de conta/contato e criação/reuso/recuperação concorrente de conversa continuam no caminho da rota. O formato de sucesso continua `{ success, message_id, whatsapp_message_id }` na rota dashboard e o envelope da API v1 permanece.

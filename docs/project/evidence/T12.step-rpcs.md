# T12 — claim/complete de dispatch step

## Escopo aplicado

Migration `20261116192433_t12_dispatch_step_rpcs` adiciona somente:

- `claim_evolution_dispatch_step(uuid, uuid, text, integer)` com os argumentos,
  defaults e colunas de retorno do contrato T12;
- `complete_evolution_dispatch_step(uuid, uuid, uuid, text, text, uuid, jsonb, text)`
  retornando `evolution_dispatch_steps`.

As duas RPCs são `SECURITY INVOKER`, fixam `search_path = pg_catalog, public, pg_temp`
e têm `EXECUTE` concedido apenas a `service_role`. A tabela de steps continua com
RLS habilitado e sem policies públicas.

## Fencing, tenant e retry

Ambas bloqueiam o root antes do step, exigem root `processing`, token correspondente
e lease vigente. `complete` também exige step `processing`, token atual e lease
vigente. Lease vencido é recusado por `complete`; `claim` pode reabrir um step
`pending` devido ou `processing` expirado, incrementando `attempts` e criando token
novo. A tentativa cinco pode executar; se expirar sem conclusão, o step vira
`failed` com `attempts_exhausted`.

As RPCs validam a linhagem root → evento → conexão Evolution → conta, a definição
e o usuário de auditoria na conta, além de conversa/contato quando presentes.
Qualquer attempt ligado precisa corresponder à conta, conexão, request e conversa
do root.

Steps novos recebem `request_id = evolution-step:<step_uuid>`. Se já houver
`send_attempt_id`, ou se a reserva existir em `evolution_send_attempts` sob a
mesma conta e request id mas ainda não tiver sido ligada, a claim retorna
`should_execute=false`. Isso inclui attempts `pending` e `unknown`; o attempt
vinculado não pode ser substituído nem o step voltar a retry `pending`. Para
transporte, o worker registra o attempt por `complete(..., 'processing', ...)`
antes do envio externo. Nenhuma RPC deste recorte envia mensagens.

`complete(..., 'pending', ...)` agenda retries sem attempt vinculado com backoff
5/15/60/300 segundos; ao atingir cinco tentativas força estado terminal `failed`.
Estados terminais limpam lease/token. Códigos de erro são limitados ao formato
`[a-z0-9][a-z0-9_]{0,47}`; texto fora do formato vira `worker_error`. Não foi
introduzido formato JSON para `result`.

## Verificação local

- `supabase migration up` confirmou o destino local `127.0.0.1:54322` e aplicou
  a migration `20261116192433`.
- Após uma correção encontrada durante o teste de reclaim, as definições finais
  foram reaplicadas pelo `psql` no container local usando `CREATE OR REPLACE`.
  A versão segue registrada em `supabase_migrations.schema_migrations`.
- `supabase/tests/evolution-dispatch-step-rpcs.sql`: passou com exit code 0 e
  `ROLLBACK`. Cobriu assinaturas, RLS/grants, root/step stale e expirados, token
  novo, request id estável, attempt cinco, backoff, erro sanitizado, isolamento
  entre contas, detecção de reservation órfã e ausência de reenvio após attempt
  `pending`/`unknown`.
- `bash supabase/tests/evolution-dispatch-step-rpcs-concurrency.sh`: passou em
  duas sessões Postgres. Ambas retornaram a mesma chave de step; só uma recebeu
  `should_execute=true`, com `attempts=1`. O script verificou cleanup exato das
  fixtures sintéticas.

As fixtures de teste usam apenas contas, eventos e conexões sintéticas locais,
placeholders sem credenciais e não executam transporte real. O teste SQL termina
em rollback; a corrida remove seus dados e verifica que não restaram linhas.

Arquivos do recorte: migration acima, os dois testes em `supabase/tests/` e esta
evidência. Nenhuma RPC de start/root completion, engine, rota ou UI foi alterada.
Sem commit.

# Evidência T09.c1-SQL — worker de eventos de conexão

**Data:** 2026-11-16
**Escopo:** três RPCs SQL de claim/fail/conclusão CONNECTION_UPDATE; sem normalizador adicional, mensagens, dispatch, produto ou cron.

## Migration e funções

- Gerada pela CLI userland 3.1.0 após `source /Users/raymozer/.local/share/wacrm-infra-a/env.sh` com `supabase migration new evolution_connection_worker`; arquivo: `20261116051422_evolution_connection_worker.sql`.
- `claim_evolution_events(integer,integer)` aceita apenas limite 1..10 e lease 1..60 s. Seleciona `pending` vencido e `processing` com lease expirada via `FOR UPDATE SKIP LOCKED`, incrementa `attempts`, define lease e token UUID novo. Tentativa 5 expirada fica `failed` sem retornar. O cleanup de expiradas está ordenado e limitado a `p_limit`; teste com 11 expiradas demonstrou que uma chamada limpa 10 e a chamada seguinte limpa a restante.
- `fail_evolution_event(uuid,uuid,text,boolean)` bloqueia a linha e exige estado `processing`, token corrente e lease vigente. Erro fora de `^[a-z0-9][a-z0-9_]{0,47}$` é substituído por `worker_error`. Falha retryable agenda 5/15/60/300 s nas tentativas 1..4; a quinta ou falha permanente vai a `failed`. Erro stale/notfound usa SQLSTATE `40001`/`P0002`.
- `complete_evolution_connection_event(uuid,uuid,text,timestamptz)` só aceita `normalized_event.kind=connection`, um estado C1 válido e timestamp finito. Sob lock e fencing atualiza a conexão derivada de `evolution_events.connection_id` somente se `state_checked_at` não regredir, e marca o evento `done` na mesma transação. Repetição terminal retorna `duplicate` sem tocar a conexão. Não lê `p_state`/`p_checked_at` do JSON; esses dados chegam do worker via `getSession`.
- Todas são `SECURITY INVOKER`, `search_path=pg_catalog, public, pg_temp`, objetos qualificados e `EXECUTE` concedido somente a `service_role`; `evolution_events` mantém RLS sem policy para clientes e grants diretos de backend restritos a `service_role`. Nenhuma função de mensagens/dispatch foi criada.

## RED/GREEN e preservação dos dados

- RED: antes da migration, o script SQL falhou com SQLSTATE `42883` porque `public.claim_evolution_events(integer,integer)` não existia; a transação foi revertida.
- Migration aplicada somente no stack local com CLI userland: `source /Users/raymozer/.local/share/wacrm-infra-a/env.sh && supabase migration up`. O destino informado foi `127.0.0.1:54322`; `supabase migration list` confirmou a migration 20261116051422 aplicada localmente. Nenhum `--remote`, npx, reset ou deploy.
- GREEN: `supabase/tests/evolution-connection-worker.sql` executado no Postgres local por psycopg em `BEGIN`/`ROLLBACK`. Passaram grants/RLS, lote 10, cleanup limitado, token de reclaim, fencing de token antigo e lease expirada em fail/complete, P0002, backoff, limite de 5, sanitização, kind/state/timestamp, transição monotônica, replay duplicate e rollback atômico.
- O teste transacional comparou snapshots agregados antes/depois de `accounts`, `profiles`, `whatsapp_connections` e **todos** `evolution_events`; foram iguais, incluindo o CONNECTION_UPDATE legítimo pending da principal. Nenhum usuário/evento sintético permaneceu após o rollback.
- Concorrência real em duas conexões Postgres: transação de controle bloqueou todas as linhas elegíveis, incluindo eventos preexistentes; segunda sessão, com `lock_timeout=1s`, recebeu zero claims em 0,124 s. Após liberar o lock, a sessão worker claimou somente o evento sintético. O claim foi revertido, e o snapshot agregado de eventos permaneceu igual. Cleanup removeu apenas conta/connection/event/user com IDs sintéticos.
- Não foi executada a suíte completa.

## Limites

Esta migration implementa somente worker SQL de eventos CONNECTION_UPDATE. Não prova processamento de eventos em worker TypeScript, normalização de mensagens, envio, cron, pareamento ou conexão WhatsApp concluída. Não houve alteração da configuração Evolution principal nem do evento legítimo pending.

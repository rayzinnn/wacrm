# Evidência T09 — worker inbound de mensagens Evolution

Data: 2026-11-16 (America/Sao_Paulo)

## Interface e implementação

- A migration separada `claim_evolution_message_events(p_limit, p_lease_seconds)` está aplicada no Supabase local pelo commit `89edd3d`. Ela reivindica somente eventos `kind=message`; a função existente `claim_evolution_events` e o worker de conexão foram preservados.
- `runEvolutionMessageBatch` reivindica no máximo 10 eventos com lease de 60 segundos. Para cada claim válido chama `apply_evolution_event(id, lease_token)` uma vez.
- Resultados `applied`, `duplicate` e `ignored` são terminais `done`; `failed` é terminal `failed`; `retry` é contado como retry. Erros SQL transitórios passam por `fail_evolution_event` com código sanitizado. Erros `40001`/`P0002` são tratados como lease stale, sem segunda aplicação nem tentativa de falha sobre o lease expirado. Erros permanentes de dados/permissão são enviados a `fail_evolution_event` como não retryable.
- O worker rejeita claims malformados e, por defesa em profundidade, não aplica payload cujo `kind` não seja `message`.
- O cron autenticado continua executando o worker de conexão e agora executa também o worker de mensagens. Os lotes são aguardados independentemente e as contagens são somadas; a resposta não inclui payloads ou conteúdo de mensagem.
- Nenhum dispatcher de automação, flow ou IA foi chamado pelo worker. A função SQL de apply pode registrar dispatches/candidatos quando um evento for processado; a execução desses dispatches não faz parte deste recorte.

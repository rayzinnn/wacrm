# T12 Flow textual node: `set_tag`

## Recorte

O menor nó faltante previsto no plano é `set_tag`: `start`, `condition` e `end`
já eram tratados pelo executor Evolution. O contrato existente
`complete_evolution_flow_transition` só grava evento, avança `flow_runs` e
conclui o ledger. A mutação de tags disponível em
`apply_evolution_automation_effect` pertence ao engine de automação e não
compõe uma transição Flow. Chamar essas operações separadamente deixaria uma
janela de crash entre efeito e cursor.

Foi preparado `complete_evolution_flow_set_tag`, que valida configuração
persistida, tenant do contato/tag, root e leases, chama a transição fenced
existente e aplica add/remove na mesma transação. A RPC é `SECURITY INVOKER`,
com execução apenas para `service_role`. A operação usa payload de auditoria
vazio; não cria formato novo de resultado. O executor mantém a action key
contratada `<transition_seq>:<node_key>`.

## Verificação e limite

Os testes mockados cobrem add/remove via uma transição, action key, config
inválida, replay sem reaplicar e ausência de chamada à transição genérica. O
SQL de teste existente ganhou fixture sintética rollback-only para verificar
grants, isolamento de tenant, mutação de tag, checkpoint do run e conclusão do
ledger na mesma chamada.

A coordenação executou localmente `BEGIN` + migration + fixture SQL com
`ON_ERROR_STOP=1`: terminou com código 0. Após `ROLLBACK`, confirmou que a
função `complete_evolution_flow_set_tag` ficou ausente. Depois da revisão,
aplicou a migration somente no Supabase local `127.0.0.1:54322` com
`supabase migration up` (exit 0). O teste SQL rollback-only foi repetido no
Postgres local com `ON_ERROR_STOP=1` e passou (exit 0). Nenhum provider,
scheduler ou capability foi chamado/ativado.

# T11 outbound media consumer evidence

Added `POST /api/whatsapp/media/send` as a server-only authenticated consumer of `media_ref.stage_id`, integrated with `createEvolutionMediaSendAdapter` and the existing durable reservation RPC.

- Request: `Idempotency-Key` (1–200 printable characters, stable per application send), `conversation_id`, `media_ref: { version: 1, stage_id }`, optional caption (maximum 4,096 characters). JSON body is capped at 16 KiB. Caller supplied recipients and extra fields are rejected.
- Recipient comes only from the authenticated account's conversation and its account-scoped contact. Phone targets are required; username/BSUID-only contacts are rejected because this Evolution media adapter accepts phone JIDs.
- Stage must be `staged`, unexpired, match the same account and conversation, and have an expected private bucket path and consistent metadata. Downloaded content is capped at 16 MiB and checked against stored byte count, SHA-256 and PNG/JPEG/PDF signature before reservation/transport.
- Application idempotency key is SHA-256-derived with account scope into a stable internal request ID. Adapter replay uses the existing reservation result and does not perform a second transport call. Ambiguous timeout remains `unknown`; HTTP output excludes provider details, credentials, and storage paths.
- The route checks the media capability before reading the request body or looking up connection/Storage. The current capability remains `media: []`, so normal requests return 422 before Storage and transport. No UI or capability was enabled; no real Evolution/WhatsApp call was made. No migration was needed.

Focused evidence: route + adapter Vitest suites passed (18 tests); scoped ESLint passed; `npm run typecheck` passed; `git diff --check` passed. Tests use synthetic bytes, mocked auth/DB/Storage/transport. No real files were staged.

# T12 — Contadores de execução no caminho Evolution

Data: 2026-11-17 (America/Sao_Paulo)

## Causa

As duas listas exibem os campos cacheados da definição: Automações lê `automations.execution_count` e `automations.last_executed_at` diretamente; `GET /api/flows` lê `flows.*` e o editor usa `execution_count`/`last_executed_at`. O motor legado chama `increment_automation_execution_count` ou `increment_flow_execution_count` ao iniciar cada execução. O RPC `start_evolution_event_dispatch`, usado pelo caminho Evolution, cria o `automation_logs` ou `flow_runs` e vincula a linha ao dispatch, mas não atualiza esses campos. O RPC de finalização da automação muda o status do log, sem alterar os contadores. Por isso os registros Evolution existem enquanto os cartões continuam em zero/“nunca”.

## Ajuste implementado

- Nova migration `supabase/migrations/20261117180755_t12_evolution_execution_counters.sql` mantém os campos cacheados e os caminhos legados.
- Um trigger soma uma execução Evolution quando um `automation_logs` recém inserido tem `evolution_dispatch_id` e a relação dispatch/automação/conta confere. Replays que reutilizam o log não disparam outro INSERT, logo não somam novamente.
- Um constraint trigger adiado observa apenas a inserção de `flow_runs`. Ele conta a execução depois que o RPC liga o run recém criado ao dispatch na mesma transação. Eventos que reutilizam um run ativo não inserem outro `flow_runs` e não incrementam o contador.
- Os updates são atômicos, mantêm `last_executed_at` monotônico e filtram por `id` e `account_id`. As funções são `SECURITY INVOKER`, com execução concedida apenas a `service_role`; as funções de trigger ignoram execuções sem vínculo Evolution.
- A migration reconcilia, uma única vez, logs/run Evolution já vinculados, somando os registros ao cache legado e usando o maior horário observado. A reconciliação de Flow usa `count(distinct flow_run_id)` para não contar múltiplas dispatches ligadas ao mesmo run.

## Cobertura adicionada

`supabase/tests/evolution-dispatch-start.sql` agora verifica que o primeiro start incrementa automação e Flow, replay de automação não duplica, replay de Flow mantém o run, uma segunda dispatch no mesmo contato reutiliza o run sem nova contagem e as definições da outra conta continuam com zero/sem horário.

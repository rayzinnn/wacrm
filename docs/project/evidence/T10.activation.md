# Evidência T10.activation — liberação controlada de texto Evolution

Data: 2026-11-16. Escopo: capability de texto, compatibilidade do resolver da API v1, testes e documentação. Os arquivos Inbox sob F4 tinham alterações existentes no worktree; foram auditados em leitura e preservados sem edição neste recorte.

## Decisão

- `getEvolutionCapabilities().text` foi ativada. `media: []`, `templates`, `broadcasts`, `reactions`, `interactive` e `typing` continuam desativados.
- A liberação foi considerada segura para texto individual porque T09 ativou a ingestão sintética com deduplicação; T03.e1 observou um único POST Evolution autorizado com HTTP 201 e ID remoto; T10 reserva antes do transporte e os caminhos de texto usam somente o adapter Evolution. HTTP 201/PENDING não é prova de delivery; esta alteração não fez envio real.
- A capability da Inbox era o único gate direto de UI. `/api/v1/messages` já aceitava texto, exigindo API key com `messages:send`, `createdBy` válido, telefone internacional e `Idempotency-Key`; tipos não texto permanecem HTTP 422. A flag não substitui esses guards.

## Bloqueio corrigido antes da ativação

- `resolveConversationByPhone` ainda exigia `whatsapp_config` e chamava `resolveAuditUserId`, que também consultava a configuração Meta antiga. Uma conta Evolution sem registro Meta falharia antes de localizar/criar conversa.
- O pré-check agora seleciona `id,created_by` de `whatsapp_connections`, filtrando `account_id` e `provider='evolution'`. Esse `created_by` auditável é usado como `user_id` nas novas linhas de contato e conversa. Dedupe por telefone, resolução de corrida, auditoria e convenção de uma conversa por contato foram preservados. `src/lib/api/v1/contacts.ts` não foi alterado.
- A rota v1 também rejeita `reply_to_message_id` antes do resolver; texto citado não suportado não cria contato/conversa antes de falhar.

## Guards auditados

- Inbox: composer continua bloqueando viewer/read-only, envio pendente, rascunho vazio e `sessionExpired`; o handler bloqueia reply antes de operação, mantém `Idempotency-Key` estável por ação/reload e não repete POST após ambiguidade. Nenhum arquivo Inbox foi alterado por causa de F4.
- `sessionExpired` é calculado pelo último inbound de cliente em 24 h. O plano Evolution C5 e a análise local do endpoint Baileys não definem a janela de 24 h da Meta para texto individual; esse guard é legado Meta e restringe o Inbox a threads com inbound recente. A API v1 não aplica essa regra. **Integração pendente após F4:** remover a condição de 24 h para envio de texto Evolution, preservando auth/read-only, capability, operação pendente, rascunho e reply não suportado. Até essa integração, o botão permanece bloqueado em thread sem inbound ou com inbound antigo.
- Rota dashboard: `requireRole('agent')`, rate limit por usuário, validação de conta/conversa ou contato e chave idempotente permanecem antes do core. API v1 usa `requireApiKey(..., 'messages:send')`, valida sender, tipo e chave antes de resolver contato.
- Core: conversa é filtrada por `account_id`; conexão/credenciais Evolution são carregadas pela conta; envio exige telefone compatível com JID individual e sender válido; reply é rejeitado. A reserva RPC precede um único POST. Replay não posta; resultado incerto fica `unknown`; o caminho de texto não usa Graph/Meta. Os efeitos de resumo/pausa no replay são idempotentes.

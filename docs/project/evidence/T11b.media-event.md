# T11b — normalização e fila de eventos de mídia

## Resultado

Implementada a normalização de referências inbound para os envelopes de imagem, documento, áudio e vídeo sustentados pela preparação de mensagens no código fixado Evolution API 2.3.7 (`cd800f2976e1e5b682fbf86a01ee4d85ae61f370`). A projeção contém apenas `contentType`, `text: null` e `mediaRef` versionada com `key.remoteJid`, `key.id` e `key.fromMe: false`; não contém bytes, URL, token, caption ou o payload de origem.

Os quatro tipos continuam desativados (`getEvolutionCapabilities().media` permanece `[]`). A fila grava esses eventos em estado terminal `failed`, com `last_error_code='unsupported_media_kind'`, `media_state='failed'` e `processed_at`; assim o worker textual existente não tenta aplicar mídia como texto nem dispara processamento posterior. Para um tipo habilitado no futuro, a fila grava explicitamente `state='pending'` e `media_state='pending'`, sem depender do default `not_required`. O teste cobre esse ramo com capability mockada; não altera a capability real. O upsert continua idempotente por `(connection_id,event_key)`. Mensagens textuais e eventos de conexão mantêm a projeção existente.

O caminho do webhook continua sendo somente normalizar, persistir e ACK. Não há download, Storage, RPC de mídia, worker de mídia, ativação de capability nem chamada ao endpoint Evolution neste recorte.

## Evidência de formato

No checkout local fixado da Evolution:

- `src/api/integrations/channel/whatsapp/whatsapp.baileys.service.ts:4652-4703`, `prepareMessage`: constrói `messageRaw` com `key`, `message`, `messageType` (`getContentType`) e timestamp. A mensagem passa por `deserializeMessageBuffers` e é enviada ao webhook. O mesmo método mapeia `documentWithCaptionMessage` para `documentMessage` antes do webhook.
- No mesmo serviço, o caminho de download mapeia os quatro nomes em `:3827-3831`; isso confirma reconhecimento no código, não capacidade runtime.
- `src/api/services/channel.service.ts:435-463` encaminha `messages.upsert` através de `sendDataWebhook`; `src/api/integrations/event/event.manager.ts:115-134` encaminha os campos `event` e `data`; `src/api/integrations/event/webhook/webhook.controller.ts:93-103` envolve esses dados no objeto com `event`, `instance`, `data`, `date_time` e demais metadados do callback.

O fixture local `infra/evolution/fixtures/message-upsert.observed.sanitized.json` é de texto. Não o apresentamos como observação de mídia. Os casos desta entrega são fixtures **sintéticas** no envelope fonte-comprovado: `messages.upsert` com `data.key`, `data.message`, `data.messageType` e `data.messageTimestamp`. Os objetos aninhados e sentinelas de URL/bytes/token/caption são exclusivamente marcadores sintéticos de privacidade; não afirmam um schema de propriedades internas de mídia nem substituem fixture runtime. `documentWithCaptionMessage`, `stickerMessage`, `ptvMessage` e outros tipos permanecem ignorados até prova específica.

## Decisão de fila para tipos desativados

A migration atual permite `state='failed'`, `media_state='failed'` e usa `last_error_code` como texto. O RPC textual instalado marca formatos não textuais com `unsupported_message_content`, que não expressaria a indisponibilidade específica exigida e ainda colocaria o evento no worker. Como esta tarefa não autoriza alterar SQL ou worker, `event-queue.ts` encerra somente os eventos de mídia cuja capability está desligada no próprio enqueue. Nenhum registro existente é sobrescrito em replay (`ignoreDuplicates: true`).

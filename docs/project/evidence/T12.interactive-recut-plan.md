# T12 — recorte para botões e listas no Flow local

O fluxo informado pelo usuário usa palavra-chave seguida de botões ou lista. A instância pareada é `WHATSAPP-BAILEYS` na Evolution API 2.3.7; o código da imagem tem rotas de envio e IDs de resposta. O WACRM ainda não executa esses nós, e não houve envio real de prova.

Sequência para liberar com segurança:

1. Normalizar `buttonsResponseMessage.selectedButtonId`, `templateButtonReplyMessage.selectedId` e `listResponseMessage.singleSelectReply.selectedRowId` como respostas interativas com ID explícito, sem aceitar eco, grupo ou URL externa. Persistir a mensagem e criar apenas a root Flow elegível; respostas interativas não devem disparar automações/IA por semelhança com texto.
2. Reservar envio interativo em tentativa durável com request ID por etapa e hash do payload inteiro. Validar conta, conversa, destinatário, configuração do nó e resultado do provider. Um resultado ambíguo não pode gerar segundo POST.
3. No Flow, enviar uma vez, guardar `message_sent`, manter o run no nó, ligar a resposta ao prompt e escolher exatamente o `next_node_key` do ID configurado. Captura, avanço e conclusão do step precisam de uma transação protegida por lease e sequência. Resposta repetida ou de outro contato não avança.
4. Integrar handoff local para os modelos que terminam na transferência de atendimento. Essa parte passou nos testes locais e está registrada em `T12.flow-handoff-local.md`. Testar botões e lista com fixtures sintéticas, dois runs concorrentes, replay e chamadas reais somente após um teste de destino consentido.
5. Liberar `interactive` e retirar o bloqueio de ativação apenas para os tipos comprovados. Manter o trabalho do usuário como rascunho durante a implementação.

Nenhum desses passos exige servidor externo; tudo permanece no localhost.

O transporte isolado e a reserva local do passo 2 passaram em testes sem envio real (`T12.interactive-send-reservation-local.md`). A ligação ao Flow ainda falta. O recebimento do passo 1 está em implementação.

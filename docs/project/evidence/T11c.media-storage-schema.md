# T11c — schema local para Storage privado de mídia Evolution

## Entrega

Criada a migration `supabase/migrations/20261116201456_t11c_media_storage_schema.sql`, gerada por `supabase migration new t11c_media_storage_schema` com Supabase CLI local 3.1.0. O timestamp 20261116201456 precede o início informado para T12 (20261116201732). Nenhuma migration foi aplicada; em particular, `supabase migration up` não foi executado enquanto T12 permanece em edição.

A migration:

- cria/atualiza somente o bucket `evolution-media` como privado (`public=false`), com limite de 16 MiB (`16777216` bytes) e allowlist MIME exata alinhada aos tipos listados no resolver T11a; não cria policy para `anon` ou `authenticated`;
- adiciona `media_sha256`, `media_size_bytes` e `media_filename` em `evolution_events`, com constraints de formato, limite, nome seguro e consistência do conjunto de metadata. O RPC grava esses campos juntos com o estado `stored`; linhas antigas com os três campos nulos continuam válidas;
- adiciona `stage_evolution_media(event_id, lease_token, sha256, size_bytes, media_type, filename)`, `SECURITY INVOKER`, executável somente por `service_role`;
- valida lease ativo/token/state, evento `message`, chave de mídia consistente, MIME compatível com `contentType`, hash SHA-256 hexadecimal, tamanho e filename seguro;
- deriva `account_id` da conexão Evolution do próprio evento e constrói o path determinístico `account-<uuid>/evolution/<event-uuid>/payload.<ext>` sem aceitar path ou account do chamador;
- retorna `staged` na primeira gravação, `duplicate` para replay com o mesmo hash/tamanho/MIME, `conflict` sem path para hash/path divergente na metadata staged e `stale` sem alteração para lease/token inválido. O nome do replay idêntico não substitui o primeiro filename persistido;
- exige `provider='evolution'` ao resolver a conta da conexão. A tabela atual também tem CHECK que só aceita Evolution; o filtro no RPC é defesa explícita adicional.

`chat-media`, sua visibilidade pública e as policies existentes não são alterados. A documentação atual do Supabase descreve bucket privado como default e permite limite e allowlist MIME na configuração do bucket ([criação de buckets](https://supabase.com/docs/guides/storage/buckets/creating-buckets)); leitura e escrita dependem de RLS em `storage.objects`, enquanto a service key ignora RLS e deve permanecer somente no servidor ([controle de acesso](https://supabase.com/docs/guides/storage/security/access-control)).

## Teste rollback-only preparado

Criado `supabase/tests/evolution-media-stage.sql`, envolvendo a fixture e mutações de dados/constraint em `BEGIN`/`ROLLBACK`. Usa usuários, contas, conexões, eventos, nomes e hashes 100% sintéticos. Cobre configuração privada/MIME/limite do bucket, preservação do bucket/policy `chat-media`, RLS habilitada e ausência de policy específica para `evolution-media`, grants e atributos do RPC, lease/token stale e expirado, path por conta, replay do mesmo hash, conflito de hash no mesmo path, SVG/tamanho/nome inválidos e recusa do provider `non-evolution`.

O schema de `whatsapp_connections` impede inserir `provider` diferente de Evolution. Para exercer a defesa do RPC, o teste remove esse CHECK somente dentro da transação rollback-only, atualiza uma terceira conexão sintética para `non-evolution`, verifica que o stage é recusado e deixa o `ROLLBACK` restaurar schema e dados. Isso não altera o schema persistente.

O teste não modifica `storage.objects`. A documentação Supabase orienta tratar `storage.objects` como metadados somente leitura e fazer uploads/updates/deletes pelo Storage API ([schema de Storage](https://supabase.com/docs/guides/storage/schema/design)). Por isso, o teste SQL valida configuração e catálogo de policies, mas não simula acesso a um objeto nem substitui o teste do endpoint HTTP/SDK. O RPC não lê nem re-hasha bytes do objeto; um worker futuro deve verificar hash/tamanho de qualquer objeto já existente via Storage API antes de reutilizá-lo e chamar o stage.

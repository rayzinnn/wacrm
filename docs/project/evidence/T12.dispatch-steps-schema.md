# T12 — schema de steps do dispatch

## Resultado

Criada e aplicada apenas no Supabase local a migration `20261116190454_t12_dispatch_steps_schema`.
Ela adiciona `public.evolution_dispatch_steps` conforme o contrato T12 e a coluna
nullable `automation_logs.evolution_dispatch_id`, com FK para o root e constraint
`UNIQUE(automation_logs.evolution_dispatch_id)`. A FK inversa usa `ON DELETE SET NULL`.

O ciclo entre `evolution_event_dispatches.automation_log_id` e
`automation_logs.evolution_dispatch_id` foi validado com a ordem definida pelo
coordenador: inserir o root, inserir o log e atualizar o root para apontar ao log.
O teste também confirma que apagar o root limpa o vínculo no log, e apagar o log
limpa `automation_log_id` no root.

## Segurança e constraints

- RLS está habilitado em `evolution_dispatch_steps`, sem policies.
- `anon` e `authenticated` não têm privilégios de tabela; `service_role` tem os
  privilégios completos previstos.
- O vínculo `dispatch_id` mantém a linhagem do step até o root/conta; a tabela
  não duplica `account_id`. Validação de tenant dentro das operações de runtime
  pertence às RPCs futuras e não foi implementada neste recorte de schema.
- O teste rollback-only verificou defaults, estado e limite de tentativas,
  `UNIQUE(dispatch_id, action_key)`, unicidade parcial de `request_id` permitindo
  múltiplos `NULL`, FKs de root/send attempt, cascata do root, negação de leitura
  para `anon`/`authenticated` e os vínculos cíclicos de `automation_logs`.
- Não houve teste de concorrência: conforme decisão do coordenador, esse teste
  fica para as RPCs de start/claim.

## Verificação local

O teste foi executado com:

```sh
docker exec -i supabase_db_wacrm-local psql -U postgres -d postgres -X -v ON_ERROR_STOP=1 -f - \
  < supabase/tests/evolution-dispatch-steps-schema.sql
```

Resultado: `BEGIN`, quatro blocos `DO`, troca de roles e `ROLLBACK`, exit code 0.
Consultas ao catálogo confirmaram as 14 colunas, seis constraints, índice único
parcial de `request_id`, RLS habilitado, zero policies e versão
`20261116190454` em `supabase_migrations.schema_migrations`. Consultas após o teste
retornaram zero steps, logs e eventos com as chaves sintéticas do fixture.

`supabase migration up --local` identificou explicitamente o alvo local
(`127.0.0.1:54322`), mas não conseguiu completar a conexão por encerramento
inesperado do Postgres durante o health check. `pg_isready` e `psql` via container
responderam; por isso o SQL da migration foi aplicado diretamente pelo `psql` no
container local e a linha correspondente foi registrada na tabela local de
migrations. Nenhum alvo remoto foi usado.

Nenhuma RPC, código TypeScript, engine ou interface foi alterada. Não houve commit.

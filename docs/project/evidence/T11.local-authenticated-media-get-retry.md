# T11 — GET autenticado de mídia sintética, outra conta

## Resultado

**Verificado no ambiente local.** O GET autenticado do dono retornou `200` e os bytes foram iguais ao PNG sintético 1×1 enviado ao Storage. O usuário sintético de outra conta recebeu `404`; a resposta não tinha tipo `image/*` e não continha os bytes do PNG. Sem sessão, a rota retornou `401`. O header `Cache-Control` do dono continha `no-store`.

## Como foi feito

- Alvo limitado a `127.0.0.1:54321` (Supabase API), `127.0.0.1:54322` (Postgres local) e `127.0.0.1:3000` (rota local). O bucket `evolution-media` foi confirmado privado antes de criar fixture.
- Criados dois usuários e duas contas sintéticas com emails `.invalid`, mais conexão Evolution, contato, conversa, evento/mensagem e objeto Storage 1×1 PNG. Nenhum dado pessoal foi usado.
- Requisições feitas uma vez para os três casos: sem sessão `401`, dono `200`, outra conta `404`.
- A limpeza no `finally` removeu objeto e registros pelos UUIDs exatos. Consulta direta no Postgres contou `0` em `auth.users`, `profiles`, `accounts`, `whatsapp_connections`, `contacts`, `conversations`, `messages`, `evolution_events` e em `storage.objects` para o path sintético.
- O script temporário foi removido após a execução.

## Limites

Este teste comprova o controle de acesso da rota apenas com fixture local sintética e PNG pequeno; não cobre mídia real, envio ou download Evolution. Não alterei rota, schema, capability, configuração de ambiente ou conta existente. A capability de mídia continua desligada; nenhum WhatsApp foi enviado. Sem commit.

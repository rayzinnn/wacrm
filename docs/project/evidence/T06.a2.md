Data: 2026-11-16 (America/Sao_Paulo)

## Escopo

Adicionada somente `public.evolution_events` conforme a seção aprovada no `schema-contract.md`, com índice de claim, RLS ativa e grants explícitos apenas para `service_role`. Não foram adicionados RPCs, dispatch, messages, bucket ou alterações em `whatsapp_connections`.

## Migration e alvo

- Supabase CLI oficial v3.1.0 em `$HOME/.local/share/wacrm-infra-a/bin/supabase`; `supabase migration new --help` e `supabase migration up --help` consultados. O arquivo `20261116045917_evolution_events.sql` foi gerado por `supabase migration new evolution_events`.
- Antes da aplicação, `public.evolution_events` não existia no Postgres local. O teste SQL falhou no primeiro insert com `relation "public.evolution_events" does not exist`, resultado RED esperado.
- `SUPABASE_ACCESS_TOKEN` foi removido do ambiente. `supabase migration up` aplicou apenas a migration pendente e informou `Target: local stack (127.0.0.1:54322)`. Não foram usados `--remote`, link, reset ou execução de migration histórica.
- Histórico local após aplicação: 59 entradas; última versão `20261116045917`.

## Catálogo confirmado

- As 16 colunas, defaults e nulabilidade correspondem ao contrato: `id`, `connection_id`, `event_key`, `normalized_event`, `state`, `attempts`, `lease_until`, `lease_token`, `next_attempt_at`, `processed_at`, `last_error_code`, `created_at`, `updated_at`, `media_state`, `media_storage_path`, `media_type`.
- Confirmadas PK, FK `connection_id` com `ON DELETE CASCADE`, unique `(connection_id,event_key)`, checks de state, attempts, media_state e coerência de `media_state='stored'` com `media_storage_path` não nulo. Índice `evolution_events_claim_idx` usa `(next_attempt_at,created_at,id)` com predicate para `pending`/`processing`.
- `relrowsecurity=true`, zero policies. ACL não concede privilégios a `PUBLIC`, `anon` ou `authenticated`; privilégios efetivos SELECT/INSERT/UPDATE/DELETE são falsos para `anon` e `authenticated`, e verdadeiros para `service_role`.

## Teste SQL transacional

Comando executado contra o Postgres local:

```sh
docker exec -i supabase_db_wacrm-local psql -U postgres -d postgres -X -v ON_ERROR_STOP=1 -f - < supabase/tests/evolution-events.sql
```

O script cria usuários, contas legítimas e duas conexões fixture em uma transação; comprova acesso negado de `anon` e dos usuários authenticated A/B para leitura, insert, update e delete; verifica gravação/atualização por `service_role`; confirma rejeição de chave duplicada na mesma conexão, aceitação da mesma chave em outra conexão, state/attempts/media inválidos e FK inexistente. O catálogo e os grants também são verificados pelo teste. Todos os blocos terminaram e o script concluiu `ROLLBACK`.

Depois do rollback: zero eventos e zero usuários fixture persistidos; uma conexão total e uma conexão real de A preservadas; as contas reais de A/B continuam sendo duas. Nenhuma credencial ou segredo foi usado nos fixtures.

## Limites

Esta etapa não implementa ingestão, claim/dispatch, processamento, mídia, mensagens, RPCs ou transporte Evolution. A migration e teste foram aplicados/verificados somente no banco Supabase local; nenhum projeto remoto foi selecionado.
